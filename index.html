RTL Architecture

A single synchronous always_ff block with asynchronous active-low reset. Priority-encoded logic handles timeout detection, early-kick faults, valid window kicks, and disabled-state bypass.

⚡
Timeout Detection
When count_reg ≥ timeout_val, wdt_reset is asserted — highest priority action, triggering a full hardware system reset pulse.
🪟
Kick Window Logic
Kick arriving before window_val sets wdt_error (early kick violation). A kick inside the window cleanly resets the counter — no fault.
🔢
Free-Running Counter
When enabled with no kick and no timeout, the 32-bit counter increments every rising clock edge. Parameterised via DATA_WIDTH for flexible deployment.
🔒
Disabled State Bypass
De-asserting wdt_enable freezes the counter at zero, clears all flags, and keeps the watchdog fully inert — no faults, no resets.

Module Interface — watchdog_timer #(DATA_WIDTH=32)

Port Dir Width Description
clkIN1System clock — 100 MHz
rst_nIN1Active-low asynchronous reset
wdt_enableIN1Enables watchdog operation
wdt_kickIN1Software kick / refresh signal
timeout_valIN32Timeout threshold in clock cycles
window_valIN32Window-open threshold
wdt_resetOUT1System reset pulse on timeout
wdt_errorOUT1Error flag for early kick violation
current_countOUT32Live value of internal counter
rrttll.sv — always_ff core
always_ff @(posedge clk or negedge rst_n) begin
  if (!rst_n) begin
    count_reg <= '0;  reset_reg <= 1'b0;  error_reg <= 1'b0;
  end else if (wdt_enable) begin
    if (count_reg >= timeout_val)
      reset_reg <= 1'b1; // Timeout expiry — highest priority
    else if (wdt_kick) begin
      if (count_reg < window_val)
        error_reg <= 1'b1; // Early kick infraction
      count_reg <= '0; // Reset counter in both cases
    end else
      count_reg <= count_reg + 1'b1; // Normal increment
  end else begin
    count_reg <= '0;  reset_reg <= 1'b0;  error_reg <= 1'b0; // Disabled
  end
end

Testbench & Test Cases

Four structured test cases cover all operational modes of the WDT. The testbench runs on Cadence INCISIVE 15.2 with timeout_val = 40 cycles and window_val = 15. A refresh_system_reset() task isolates each test case from state leakage.

TC-01
✓ PASS
Normal Operation — Valid Window Kick
WDT is enabled. Wait 25 cycles (beyond window_val = 15), then assert kick for 1 cycle. Counter must reset to 0 cleanly; no error or reset signal should be raised. Counter snapshot reported as 1 due to one-cycle pipeline latency — assertion correctly accepts count == 0 || count == 1.
if (current_count == 0 || current_count == 1)
  $display("[ASSERT PASS] Counter reset cleanly inside open window.");
TC-02
✓ PASS
Fault Injection — Early Kick Violation
After TC1, wait only 5 cycles (count < window_val = 15) before asserting kick. The WDT should detect the premature kick and assert wdt_error as a protocol violation flag.
if (wdt_error)
  $display("[ASSERT PASS] Watchdog early kick violation flagged successfully!");
TC-03
✓ PASS
Fault Injection — Timeout Expiration / Hardware Reset
Enable WDT, wait 45 clock cycles without issuing any kick (timeout_val = 40). The watchdog must assert wdt_reset after cycle 40, triggering a simulated hardware system reset pulse.
if (wdt_reset)
  $display("[ASSERT PASS] Watchdog timed out successfully! Hardware reset asserted.");
TC-04
✓ PASS
Disabled State — Counter Bypass Verification
De-assert wdt_enable, issue a kick, and wait 8 cycles. The counter must remain frozen at zero; no faults or resets should be generated. Confirms the WDT is fully inert when disabled.
if (current_count == 0)
  $display("[ASSERT PASS] Watchdog counter stayed locked at 0 while disabled.");

Design Observations

Noted for the next design iteration.

Early Kick Counter Clear Behaviour
On early kick violation, the counter is currently cleared even though a fault is flagged. Depending on system intent, it may be preferable to let the counter continue running so the timeout still expires unless a system reset is issued. Design decision to clarify with architect.
Sticky Fault Registers
error_reg and reset_reg are only cleared on rst_n or disable. For production SoC integration, a write-to-clear register interface is recommended.
No Metastability Guards
wdt_kick and wdt_enable are used directly without synchronizer flops. If driven from a different clock domain or asynchronous software context, two-flop synchronizers should be added at the input boundary.
Coverage Boundary Conditions
Future stimulus to complete boundary coverage: kick exactly at window_val, kick at timeout_val - 1, toggling wdt_enable mid-count, and dynamically changing timeout_val during operation.
